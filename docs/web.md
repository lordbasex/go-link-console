# The website

`frontend/` is React + TypeScript with npm workspaces. Each build is a static folder that any static web host can serve.

| Package | What it is |
|---|---|
| `packages/shared` (`@go-link/shared`) | Protocol types, the signaling client, server selection, the WebRTC player, the 9-digit code, room metadata validation, SHA-256/HMAC and the design tokens (`tokens.css`) |
| `apps/web` (`@go-link/web`) | The website |

## Development

```bash
cd frontend
npm install
npm run dev          # http://localhost:5180, both sites on one origin
npm test             # every test (vitest)
npm run typecheck
npm run build        # apps/web/dist-site and dist-play, ready for a static host
```

A single test:

```bash
npx vitest run apps/web/src/app.test.tsx -t "links a device"
```

Against a local signalhub:

```bash
LIVE_SIGNAL_URL=ws://127.0.0.1:8090/ws npx vitest run packages/shared/test/live.test.ts
```

A local signalhub must accept the dev server's origin in its `ALLOWED_ORIGINS`.

### Configuration (`apps/web/.env.local`)

Template: [`apps/web/.env.example`](../frontend/apps/web/.env.example).

| Variable | Description |
|---|---|
| `VITE_SIGNAL_URL` | Default signaling server. Local: `ws://127.0.0.1:8090/ws`. Production: `wss://signal.go-link.org/ws` |
| `VITE_DEMO_DATA` | `true` shows sample data (rooms, players, chat) instead of real data |
| `VITE_ROLE` | `site` or `play` builds one of the [two sites](#two-sites); empty (development) serves both on one origin |
| `VITE_SITE_URL`, `VITE_PLAY_URL` | The two sites' addresses. Default: `https://go-link.org` and `https://play.go-link.org` in a build, `http://localhost:5182` and `5183` in development |
| `VITE_MAKER_URL` | Willy Maker's site, trusted by `/maker-bridge`. Default: `https://maker.go-link.org` in a build, `http://localhost:5181` in development |

STUN and TURN are **not** configured: they arrive in signalhub's `hello` and live only in memory.

## Two sites

The website is built twice from `apps/web` (`src/role.ts`), each on its own origin:

| Build | Address | Pages |
|---|---|---|
| `site` (`dist-site`) | go-link.org | The landing, the guide (`/docs`), the tools (`/tools`, skin editor, mini-games), the picture demo, `/handoff` |
| `play` (`dist-play`) | play.go-link.org, and the device's local panel | The rooms (`/rooms`, `/create`, `/r/<id>`), invitations (`/g/<invite>`), My device (`/device`) |
| both | | `/test-controller` (its settings are the ones rooms and mini-games use), `/maker-bridge`, `/terms`, `/privacy` |

- **Why:** the link to the device lives in the rooms' origin storage. The landing, the guide and the tools never see it, and the landing never connects to the signaling server (`SignalProvider offline`), so nothing on those pages can reach the device.
- **Links between them:** a page of the other site is reached through the router like any page; the catch-all route (`Elsewhere` in `App.tsx`) sends the browser to the other site's same path, query and fragment. On play, the logo and "How it works" go to the landing. Each build's own pages are chosen by the build constant written out in `App.tsx`, so the other site's pages are not in the build at all.
- **Invitations** are always shared as `go-link.org/g/<invite>` (`invitationUrl`): the Player apps open that address, and the landing sends browsers on to play. "Join a game" on the landing goes to play's join page, because the PIN travels in the page's history state, which never leaves its origin.
- **Handoff:** before the split everything ran on go-link.org, so a browser may still keep its device link, room passes and settings there. While it does, the landing's links to play add `?import=1`, and play offers to bring them: a click opens `go-link.org/handoff`, which posts every `go-link.*` setting except the landing's own (Willy Maker games, skins) to play's origin only; play stores the ones it does not have yet, answers `done`, and the landing then forgets the device link and the passes (`src/handoff.ts`, [security](security.md#the-two-sites-and-the-handoff)).
- **Development:** `npm run dev` serves both on one origin. `npm run dev:site -w @go-link/web` (5182) and `npm run dev:play -w @go-link/web` (5183) run each build on its own origin.

## Languages

All visible text lives in `apps/web/src/i18n/`: `en.ts` (English, default and reference), `es.ts` (Spanish) and `pt.ts` (Brazilian Portuguese), with exactly the same keys (the `Messages` type checks it at build time). The EN · ES · PT switch in the header changes the language live, without reloading, so a running game is not interrupted. The choice is kept in `go-link.lang` and reflected in `<html lang>`. To add a language: another file with the same shape and an entry in `LANGS` (`i18n/index.ts`).

## Picture styles

Games arrive at their native size (384 × 224, 320 × 240…), or enlarged 2x by the device (768 × 448…, the High and Normal [video qualities](device.md#video-quality)), with a display aspect (`live.aspect`, 4:3 for arcades). The site's default is **Smooth** with **Ambient** sides (`DEFAULT_STYLE`, `DEFAULT_BANDS` and `SITE_DEFAULT` in `picture/settings.ts`); Smooth with Black sides is the browser enlarging the `<video>` itself (bilinear). The room's **Picture** settings (`components/PictureControl.tsx`, opened from the header's "…" menu; on the touch pad a dock button; a bottom sheet on phones, and a **Picture** button in the console drawer's You tab) with two of the site's `Select`s and a **Compare** switch. The choice is per viewer, applies at once without a reload (a `go-link:picture` window event keeps every mounted control in sync) and is kept in localStorage `go-link.picture-style` (`smooth`, `sharp`, `crt`, `edges`) and `go-link.picture-bands` (`black`, `ambient`, `frame`).

- **Room default**: the host may give each room a default picture (`room_action` `picture`, see [protocol.md](protocol.md#room-picture-default)), which guests get in `room_state.picture`. Precedence, per value (`resolvePicture`): the viewer's own saved choice, else the room's default, else the site's. `usePictureSettings(room)` returns the picture, the setter and `{saved, reset}`. The Picture popover shows "Room default: *style* · *sides*" and, when the viewer's choice differs, **Use the room's default** (**Use the default** in a room without one), which forgets the saved choice (`clearPictureSettings`) so the viewer follows the room from then on. The room's owner (a linked browser in its own room or the test pattern room) also gets **Set as the room's default**, which sends the current picture; once the device echoes it back, the popover says "This is the room's default.". In the Rooms page, each own room's ⋯ menu has **Picture default**, and My device has a picture button next to the test pattern room: both open `RoomPictureDialog` (Style and Sides selects, Save, Use the default, Cancel). The stage carries `data-picture-style` and `data-picture-bands` for tests.
- **Renderer** (`src/picture/`): `PictureCanvas` draws the room's `<video>` into a canvas with WebGL 2, else WebGL 1 (the shaders are GLSL ES 1.00, so the same code runs on both), else nothing: `onRenderer(null)` and the plain `<video>` stays. It runs only when needed: Smooth with Black sides is exactly the browser's own look, so no canvas is created. It draws once per new video frame (`requestVideoFrameCallback`, else every `requestAnimationFrame`), again on resize or a setting change, and nothing while the page is hidden; a lost GPU context is asked back (`preventDefault`) and rebuilt on `webglcontextrestored`. The canvas is sized in device pixels (`devicePixelRatio`), capped at a 4K screen's pixel count.
- **2x streams**: `useHostStream` keeps `stream_stats.video` (`parseStreamVideo`, see [protocol.md](protocol.md#video-scale)) as `live.video`. When `scale` is 2, `PictureCanvas` gets the game's size (`native`) and the renderer first averages each 2 × 2 block of the frame into a texture of the game's size (`DOWN_SHADER`, four samples at texel centers), and every style, the smooth edges pass and the ambient light read that texture. It only does so when the frame is exactly twice that size (`workingSize`), so frames of the old size during a quality change are drawn as they are. A 2x nearest-neighbour picture drawn this way is identical to the native one in every style (checked in Chromium on the test card); drawn raw, CRT would draw twice the game's scanlines. The plain `<video>` (Smooth with Black sides, or no WebGL) changes nothing. The stream figures (the (i) button, `StreamInfo`) show **Video** ("768×448 (2× of 384×224)") and **Quality** ("High", or "Saver (CPU)").
- **Layout** (`layout.ts`): the picture is the largest rectangle with the display aspect that fits, centered (`fitRect`); it never crops. The canvas (`.picture-layer`) covers the stage, or in console mode exactly the screen box `--sx/--sy/--sw/--sh`, so the overlays still line up. The `<video>` stays underneath, playing the sound and keeping its state, so screenshots (`saveScreenshot` reads the video), recordings, full screen, console mode and the stage's tap handling are unchanged (the canvas has `pointer-events: none`).
- **Styles** (`shaders.ts`, written for go-link): *Smooth* is bilinear. *Sharp* keeps each game pixel flat and blends across each pixel edge over one screen pixel (integer-free "sharp bilinear"), so pixels stay square at any scale without shimmer. *CRT arcade*: gaussian beams per game line whose width grows with brightness, faded out below about 3 screen pixels per line (no moiré on small screens); an aperture grille (RGB columns at the screen's own pixel density); barrel curvature normalized so the edge midpoints stay and the corners come in (the whole picture stays visible inside a rounded tube); a small glow of the bright parts; the math in linear light. No noise or flicker is ever added. *Smooth edges* (experimental, our own algorithm, not xBR/HQx/xBRZ code): the game is drawn at an integer enlargement per axis into a texture where each quarter of a pixel whose two outer neighbors match each other (and differ from it, while the opposite neighbors differ from them) is cut along its diagonal; then that texture is shown like Sharp.
- **Sides**: *Black* (`--color-video`); *Ambient*: each frame is shrunk to a 32 × 24 texture (a 4 × 4 box filter per texel, blended over the last one so the colors glide; slower with `prefers-reduced-motion`), sampled with a two-ring blur, enlarged to cover the stage, darkened toward the edges and dithered; *Frame*: an arcade cabinet surround drawn in the shader (a bezel that hugs the picture, which is inset a little so it always shows, the panel, a lit trim in the accent color and a speaker grille in each wide side band). The shader colors are tokens (`--picture-cabinet`, `--picture-cabinet-2`, `--picture-bezel`, `--picture-bezel-hi`, `--color-accent`, `--color-video`) read with `getComputedStyle`.
- **Compare**: a split line over the video (`SplitDivider`: a `role="slider"` handle, drag or arrow keys); left of it the shader draws the browser's look (Smooth, Black sides), right of it the choice.
- **Refresh rate**: `useRefreshRate` (`refreshRate.ts`) measures the median `requestAnimationFrame` interval over 60 frames every 5 s and snaps it to a common rate; the room's stream figures show **Screen** (measured only while they are open) and **Picture** (the style and WebGL version, or Browser), and Test your controller shows **Screen**.
- **`/picture-demo`** (`pages/PictureDemoPage.tsx`): the same choices on a synthetic arcade frame (`testCard.ts`: a PM5544-style card with a grid, color bars, gray steps, 1-4 pixel gratings, diagonals, a circle, a pixel-font clock and moving sprites, drawn at 384 × 224 and shown at 4:3) with the divider and a full screen button. In a room, Compare does the same with the live game.
- **Quality lab** (development only): `/picture-lab` exists only in `npm run dev` builds (`import.meta.env.DEV`; the route and its chunk are not in the production build) and is not linked anywhere. `?src=` takes a same-origin path (for example an image put in `apps/web/public/lab/`, which must not be committed) or `testcard`, `?aspect=4/3`, `?bands=black|ambient|frame|all` and `?up=2` (the source enlarged 2x with nearest neighbour and drawn as a 2x stream; `&native=0` draws it raw); it renders every style at 1920 × 1080 and 3840 × 2160 with `renderStill` (`renderer.ts`, usable from any code) and exposes the PNG data URLs as `window.__pictureLab` for a script, with `data-lab-ready="true"` when done.

## Test your controller

`/test-controller` (`pages/TestControllerPage.tsx`) needs no device: `components/TestPad.tsx` draws the test pattern's controller (the same layout and lamps as `pkg/testpattern` on the device, colors from the `--tc-*` tokens, the same in both themes) and lights what the keyboard (with this browser's key map), the on-screen gamepad (`TouchPad`, shown with a button) and every Gamepad API controller press, with each gamepad's name. **Input to screen** is the time from the input event (`KeyboardEvent.timeStamp`, `Gamepad.timestamp`) to the next `requestAnimationFrame`, last and average of 20: the page's own share of the delay, without the network or the game. Linked from the guide's Controls page and the room's How to play.

The page also gives every connected controller its own card (`tools/PadTester.tsx`). `controllers/controllerModels.ts` (a shared module with the drawings, used by this page and by the Destroy game; styles in `controllers/controllers.css`) reads the USB vendor and product ids from `Gamepad.id` (Chrome writes `Vendor: 057e Product: 2009`, Firefox `057e-2009-…`) and names the brand and model (Switch Pro, Joy-Con, DualSense, DualShock 4, Xbox 360, Xbox One/Series, 8BitDo), falling back to the name, and `buttonNames` gives each model's printed button names; `controllers/ControllerModel.tsx` draws each one as it is, with our own vectors and no logos, lighting what is pressed and moving the sticks. `tools/diagnostics.ts` holds the measurements, tested without a controller: **drift** (the stick's average at rest and its trembling), **circularity** (the farthest point in 36 directions against a circle, once 90 % were reached), **dead zone** (the smallest jump away from exactly 0), **triggers** (deepest pull, the time back under 2 % and what stays pressed at rest), **bounce** (a press less than 40 ms after the same button was let go) and the **updates per second** (new `Gamepad.timestamp`s in the last second). **Run the check** walks through rest (3 s), turning each stick, pulling the triggers and pressing every button, then shows each result as Good, Worth a look or Problem. Vibration uses `vibrationActuator.playEffect("dual-rumble")` where the browser has it. The update rate shows the highest rate seen while the controller was used (`PollingRate.peak`), since many browsers only report a controller when it changes. **Event log** opens a terminal next to the cards (`tools/PadConsole.tsx`, the cards stay on the other half; hidden, the page is as before): `tools/padLog.ts` writes every change between frames, stamped with the controller's own report time (buttons with their press length, sticks when they move 0.1, analog triggers every 10 %, connections, and bounces as warnings), keeps the last 5000 lines, and filters by kind and controller, with pause and clear. **Copy report for AI** and **Download report** build a Markdown report (`buildReport`): short instructions for an AI assistant (answer in the page's language), the environment, per controller its ids, rates, the page's checks, sticks, triggers and every button's presses, bounces and press times, the buttons never pressed, the last 400 log lines and the raw data as JSON. Nothing is sent. Browsers don't say whether a controller uses USB or Bluetooth, and worn rubber can't be measured; the page says so. Nothing is stored.

## Controller mini-games

`/tools/games` (`pages/GamesPage.tsx`, lazy; `?g=<game>` opens one) runs six short games on a 320 × 200 canvas board, each one a test in disguise: **Link** (turn cable tiles until the signal reaches every player; D-pad, buttons 1 and 2, L and R), **Snake** (counts each direction used), **Memory** (repeat a sequence on buttons 1 to 4; times the answers and counts double presses under 40 ms with the tester's `BounceProbe`, without holding them against the player), **Paddle** (the stick moves the paddle with almost no dead zone, so a drifting stick makes it creep; a raw value between 0.05 and 0.35 held still for a second shows a drift notice), **Racer** (R2 speeds up, L2 brakes, the stick steers for 60 s; keeps each trigger's deepest pull and whether it answered in between) and **Special moves** (motions in numpad notation, e.g. ↓↘→ + 1, with the time from the last direction to the button graded Perfect ≤ 50 ms, Great ≤ 120 ms, Good ≤ 220 ms). Each game's rules are pure modules in `src/games/` (tested without a DOM); `games/views.ts` draws them in the stage's colors (`.stage-tokens`, so the board stays dark in both themes) and every word is in the page, translated. Input is every Gamepad API controller (standard mapping) plus the keyboard (arrows, Z X A S, Q W, E R, Space); a key tap shorter than a frame still counts. The Link generator builds a random tree over all its cells before turning the tiles, so every board can be solved. A **How to play** panel beside the board (under it on narrow screens) gives each game's goal, a controls table (controller and keyboard), the points and what the result says about the controller. **Sound**: `games/sound.ts` is an 8-bit style chip made with the Web Audio API alone (square, triangle and sawtooth oscillators and a noise buffer, no sound files) with an original music loop per game and an effect for every action; the rules only name events through `games/sfx.ts` (`sfx("eat")`, a no-op without a sink, as in the tests), the Racer's engine follows the speed, and the bar has music and sound switches (kept in memory only). Browsers start audio only after a click or a key, so the first one unlocks it. **Touch**: phones and tablets (`pointer: coarse`, or the first touch on a hybrid screen) get an on-screen pad under the board (`components/GameTouchPad.tsx`) with only what each game uses: an 8-way D-pad you slide across, the face buttons in their diamond, L, R and Start (Link), a steering slider (Paddle, Racer) and gas and brake pads whose depth follows the finger's height (Racer); several fingers work at once, and a swipe on the board turns the snake. It writes a `TouchInput` that `addTouch` merges into the same frame as the keyboard and controllers (a tap shorter than a frame still counts), so the rules don't change. **Effects**: the events carry where they happened (`SfxAt`: board position, points, a palette color) and `games/fx.ts` draws particles (bricks, the snake eating, a cleared level, good special moves), points floating up, a flash (a cleared level, Perfect, game over) and a short shake (losing a ball, leaving the road, game over) over the board, and the lit Link cables carry a pulse from DEV; with `prefers-reduced-motion` there is no shake and a third of the particles. The mini-games are for the website only: they are never part of the Player apps. Nothing is stored: the best score lives in memory while the page is open.

## Destroy this page

The header's devil, shown only on the landing (`/`), opens its easter egg: a mission where the go-link hero breaks the page apart and rescues the people trapped in it, with an alarm, sound and the controller, keyboard or a touch pad. Everything runs in the browser (HTML, canvas, Web Audio); nothing is stored and nothing is sent.

It is a self-contained module, `src/destroy/`, so it could become a standalone game or run on any other page:

| Folder | What it holds |
|---|---|
| `index.ts` | The only public entry: `startDestroy({ root, messages, assetBase, onExit, reducedMotion, debug })` returns `{ exit() }`. `root` is any element; the landing passes `#root` (the whole app). |
| `engine/` | Pure TypeScript, tested alone: the world of bodies (`world.ts`, damage, chain destruction, the destroyed share), a spatial grid and ray casts (`grid.ts`), gravity and one-way ledges (`physics.ts`), the hero (`player.ts`), the people to rescue (`civilian.ts`), debris (`particles.ts`), animation frames (`anim.ts`) and the mission (`game.ts`). |
| `host/` | The DOM adapter: `stage.ts` lays an inert copy of the root over the real page (hidden with `visibility`, so its size and scroll stay; leaving removes the copy and shows the page untouched), `atomize.ts` splits every text into one span per word, `scan.ts` turns words, pictures, buttons and painted boxes into bodies with page coordinates, `effects.ts` punches bullet holes with CSS masks and drops clipped copies of broken parts, `input.ts` merges keys, Gamepad API controllers and touch, `render.ts` draws the characters, bullets, rockets, blasts and debris on a canvas fixed over the window, and `session.ts` runs the loop and the camera (it scrolls the window after the hero). |
| `assets/` | The character atlases (`atlas.ts`): loading and drawing frames by their feet. |
| `audio/` | An 8-bit style chip (Web Audio, no files): alarm siren, an action loop, gun, knife, bazooka, breaks, rescue jingle and the mission complete fanfare. |
| `ui/` | The interface in atomic design: `atoms.tsx` (capsule button, counter chip, person icon, weapon chip), `molecules.tsx` (HUD bar, weapons, controls table, touch pad), `organisms.tsx` (alarm, briefing, HUD, pause menu, mission complete) and the `DestroyApp.tsx` template; its own `destroy.css` (tokens only, dark in both themes). |
| `messages.ts` | The texts it needs, passed in by the host (`t.destroy` in `en.ts`/`es.ts`/`pt.ts`). |

The page's parts are bodies: every word, picture, button and bounded painted box (a card, a panel, a chip), counted only when really visible (`checkVisibility` with opacity and visibility, on the page sideways, and not mostly clipped by a scrolling or clipping container). Their tops are one-way ledges; a wide layout band (a painted box wider than 70 % of the window: the header bar, section backgrounds, page wrappers) is background: the hero falls through it, bullets pass it, it crumbles by itself once nothing is left over it or inside it, and it never counts. Health by kind: word 12, button or chip 30, picture 45, box 105 (whatever its size); damage: machine gun 4 per bullet at 10 a second, knife 12 per slash at 2.5 a second (short reach), flying kick 16, bazooka 40 on what it strikes plus 18 to everything within 80 px, one a second. A shot is a ray through the grid that hits the nearest piece or villain; a hit piece shows a capsule health bar (green, amber, red) that eases down and fades 2 s after the last hit, and gun hits punch holes with CSS mask gradients. A broken piece hides in place (no reflow) with everything on it. The last few pieces (5 % or less) crumble by themselves after 20 s without a hit, and radar arrows on the window's edge point to what is out of sight: the nearest part left (a brick), people to rescue (a head) and villains (a skull), each with its distance.

The mission, Willy Gorklingo against the Lag gang: people to rescue (one per ~800 px of page, 6 to 16, the four kinds mixed) are hidden at random inside pieces, one per band of the page, with a seeded generator (`Game` takes `seed`). They shout HELP! until reached (within 48 px, from the same ledge or near it, or by touching them), cheer, then a beam of light lifts them away (+1): anyone still on screen is someone to rescue. The Lag gang (one per ~700 px, 3 to 14; `engine/enemy.ts`): Glitch-9 (robot, 120), Vera Buffer (80) and Jitter (alien, 100), each in four outfits (the clothes' hue turned at load, `assets/atlas.ts recolor`). They walk a short beat, shoot only with a clear line of sight (a ray through the grid) after a 0.5 s warning (a flash and "!"), hit up close, and move to another spot when their cover breaks. The first time Willy hurts one it turns angry for good (red outline, an angry face) and warns the others within 500 px: angry ones chase him across ledges (drop through, hop up, jump attacks), warn for 0.25 s and fire about twice as often; at most three shoot at once, and their shots are slow glowing balls stopped by whole pieces. Willy has 4 lives with 100 health each (a shot takes 10, a blow 15, then 1 s of grace); losing a life he blinks untouchable for 2 s on the nearest ledge above; a broken picture or box sometimes drops a heart (health, or a life when full). The mission has 10 minutes (`Mission time` counts down, red and blinking in the last minute, the music hurries). It is complete when 100 % is destroyed, everyone is rescued and the gang is defeated: the mission bar weighs 60 % destruction, 25 % rescues and 15 % the gang (70/30 without enemies) and reaches 100 only then. Out of time or out of lives: MISSION ABORTED, with the stats, Try again or Rebuild the page. Restart (a new copy, new hiding places) and Unstuck (back onto the nearest ledge above) are in the HUD and the pause menu; Esc or Start pauses and resumes.

Moves: walk, run (full tilt, Shift or R1), jump (held: higher), double jump, a jetpack after the double jump while jump is held (3 s of fuel, a bar under Willy, full again after 1 s on the ground, and a rescue tops it up), crouch and crawl, drop through a floor (down + jump), flying kick (knife in the air), machine gun (also in the air) aimed in 8 directions (up or down alone: straight; with a direction: 45°), knife (held: keeps slashing; with down, at the feet), bazooka (with down, at the feet) and rescue. Animations used: idle; run; turn (a quick turn when he changes direction); jump (take-off, rising, top, falling, landing); jump_kick; crouch and crawl; machine_gun and the aim poses aim_up45, aim_up, aim_down45, aim_down (by the aim; the horizontal frames when missing); knife; bazooka; yawn after 6 s idle, then bored (a sleepy loop) until any input; thumbs_up on a rescue. The civilians use worried (waiting), happy and thanks (the woman) while cheering; the villains idle, walk, shoot, melee, jump_attack (angry leaps), jump, hit and defeated. Resizing the window pauses: the copy no longer matches, so resuming starts again. Reduced motion: no shaking, fewer particles, no alarm animation. The game is a separate chunk loaded on the devil's first click (`src/destroyLauncher.ts`). Its interface and canvas are marked `data-destroy-ui`: the scan skips them and the effects only ever touch the page copy; a guard (`ui/Guard.tsx`) draws the interface again if a screen fails, so the overlay can't vanish while the game goes on. Development builds expose `window.__destroy` (`finish()`, `peek()`, `drive()`, `skipTime()`) for scripted checks.

Loading: the pointer or the focus on the devil (and the direct link at once) starts downloading the game's chunk and the five atlases (`prefetchDestroy` in `destroyLauncher.ts`), the briefing opens at once with shimmering skeletons in the characters' places and Start showing Loading… until the pictures are in, then they fade in (no shimmer with reduced motion); the direct link opens the game as soon as the landing exists and lifts the startup logo itself. Controllers are read through this browser's map for that model, like the controller test (`go-link.input` in localStorage, `padMapFor` + `padBits`, in `host/pad.ts`), so a generic USB pad the test shows correctly plays the same in the game and lights its help; a button held when the browser first lists the pad counts again once let go (`readGamepad` in the shared package).

The characters are the user's own sprite sheets: `frontend/apps/web/scripts/destroy-atlas.mjs <sheets dir>` cuts each animation's right-facing frames out of the sheets' regions (the background keyed to transparency from the region's edge, labels and separator lines dropped, parts joined, a feet pivot), and packs one atlas per character into `public/destroy/` (`player`, `npcs`, `robot`, `blonde` and `alien`, each a picture and a `.json` that names it): lossless WebP (`cwebp -lossless -exact`, about a third lighter than PNG, the same pixels) when `cwebp` is installed, else PNG. It needs the e2e workspace's Playwright; `DEBUG_ATLAS=1` also writes each sheet with the found frames boxed.

## Recordings and MP4

The host records a game from the room's dock; everyone sees REC and a chat notice. When a recording ends, the host's browser offers to download it: the WebM comes from the device in 60 KB parts over the `files` DataChannel (progress, cancel, SHA-256 check), and then **the browser** turns it into an MP4 that chat apps and phones play ("Preparing the MP4 video…"). The device takes no part in the conversion:

- `frontend/wasm/mp4` is a small Go program compiled to WebAssembly (`make -C frontend/wasm/mp4 build`, run by `make web-build`; output in `apps/web/public/mp4/`, not committed). It reads the WebM (frame positions only, nothing copied) and writes a progressive MP4 with the index first. Tests run on the computer (`go test ./...`, one of them muxes a real ffmpeg stream and decodes it back).
- `apps/web/src/components/toMp4.ts` uses WebCodecs: VP8 is decoded, enlarged by whole steps without smoothing (up to 900 px high) and encoded to H.264; the Opus tracks are decoded, mixed five seconds at a time and encoded to AAC. When someone spoke there are three sound tracks, alternatives of one another (a player plays one): 1 the game and the voices mixed (the default, what phones and chat apps play), 2 the game alone, 3 the voices alone. When the recording has voices (its `tracks` list `voice-pN`), the saved dialog offers "Preview and export" and, once downloaded, shows a preview before converting (a recording without voices is converted right away, there is nothing to mix): the <video> plays the picture and the game, the voices are decoded a few seconds ahead and played with Web Audio, and a Game and a Voices volume (0-300 %) plus a clipping meter set the mix; a soft limiter keeps peaks from crackling (`RecordingPreview.tsx`).
- Browsers without WebCodecs or without an H.264/AAC encoder save the original WebM instead, and say so. The CSP allows `'wasm-unsafe-eval'` for this.

Screenshots are browser only: the camera button draws the `<video>` into a canvas and saves a PNG.

## Design system

- **Capsule UI:** every button is a 36 px capsule; icon-only buttons are 36 px circles with a tooltip (`data-tip`). Inputs, selects and segmented controls are capsules too. Touch devices get an invisible 44 px hit area. Square buttons are never mixed with capsules.
- **Select (`components/ui/Select.tsx`):** the site's own dropdown, used instead of the browser's `<select>` (whose open list the system draws): the Microphone and Output device lists, "Plays as" and "Keyboard plays as" in the controls panel, and the ROMs tab's Sort. Closed it is a capsule button (value with an ellipsis and a chevron); open, a listbox in the page's surface with a check on the current option, the accent on the highlighted one, an optional second line per option and a scroll past 320 px. It is portaled to `document.body` (or the full screen element) with `position: fixed`, flips above the button when there is no room below and stays inside the window, so no popover, drawer or dialog clips it; a list opened from a control over the video keeps the video's dark colors (`.stage-tokens`). It follows the WAI-ARIA select-only combobox pattern: a `role="combobox"` button with `aria-haspopup="listbox"`, `aria-expanded`, `aria-controls`, `aria-labelledby` its `<label>` and `aria-activedescendant` (the focus never leaves the button); Enter, Space and the arrows open it, the arrows, Home, End and Page Up/Down move, typing jumps to the first option that starts with it (repeating a letter cycles), Enter or Space picks, Escape and Tab close. The keys it uses and the presses inside the list never reach the page, so Escape or a pick does not close the popover around it and the arrows do not move a player in the game. Options are 44 px high on touch screens.
- **Tokens:** colors exist only as tokens in `packages/shared/src/tokens.css`: `:root` is the dark theme (default) and `:root[data-theme="light"]` the light one. Never hardcode a color: add a token with both values. The video stage (`.video-stage`) keeps the dark tokens in light mode.
- **Theme before paint:** `public/theme.js` applies the saved theme (`go-link.theme`) before the page paints. It is a separate file because the CSP forbids inline scripts.
- **Shared pieces:** `PageHero`, `Chip`, `HeroTile`, dashboard cards, `GamePicker`, `ControllerArt`, the ROM and room tables.
- **Loading:** the startup intro (`#splash` in `index.html`, `public/splash.css`, plain HTML and CSS so it shows before the app loads) stays at least 3 s and until the first screen has real data (`useSplash` in `App.tsx`, max 8 s). On a dark radial background the go-link icon pops in with a soft orange glow, "go-link" rises at 0.6 s and **INSERT COIN** rises at 1.1 s and blinks (four times at most). INSERT COIN is drawn as 5x7 pixel letters in an inline SVG (no font file), the same letters the apps draw, and reads the same in every language. It stays dark in both themes. With reduced motion everything just fades in. A tap, click or key skips it (`src/intro.ts`), and that first gesture also plays the **coin sound** (`src/coin.ts`: three quick square-wave notes made with Web Audio, an original sound, no file) when the intro still shows or within the first 4 s; browsers block sound before a gesture, so without one it stays silent and never asks. After that, views show skeletons (`components/ui/Skeleton.tsx`), never an empty list that fills later. Long lists page with `useInfiniteList`; the ROM library is paged by the device itself (`useRomPages` and `useRomsByName` in `components/device/useLibrary.ts`, over `roms_query` and `roms_get`): the website never holds the whole library, which can be thousands of sets.
- **Fonts:** Chakra Petch, IBM Plex Sans and JetBrains Mono (SIL Open Font License) are bundled with the site (`@fontsource`), never loaded from a font service, so no third party receives visitors' IP addresses.
- **Icons:** `public/favicon.svg` is the header logo. The PNG icons come from `backend-device/pkg/trayicon.Render`, the same drawing the device uses for its app and tray icon.
- **Accessibility:** real `<button>` and `<a>`, `<label>` on inputs, `aria-label` on icon-only buttons, one `<main>` per page. The end-to-end tests run axe on every page.

## Security

- A strict CSP in the production build (`connect-src 'self' wss:` to allow your own signaling servers). It does not apply in development, because Vite needs inline scripts.
- Anything written by other users (room metadata, names, chat) is always rendered as text.
- See [security.md](security.md).
